## Findings

Priority meanings: **P1** = resolve before the affected release or workflow is relied upon; **P2** = next hardening increment; **P3** = maintainability improvement after correctness. “Reproduced” means a local probe demonstrated the behavior. “Code-confirmed” means the control flow establishes the gap; it does not imply an observed production incident.

### REV-01 · P1 · Named profiles can inherit the default cookie

**Reproduced.** In [client-factory.ts](../src/client-factory.ts), lines 41–46, `cookie` starts with `FUSEBASE_COOKIE`. A named profile only replaces it when its stored cookie exists. A nonexistent or token-only profile therefore retains the default account's cookie. Tools accepting an explicit `profile` can reach this path without using `switch_active_profile`. The synthetic probe confirmed `buildClient('nonexistent_review_profile')` receives the default cookie.

**Impact:** a request intended for a separate profile can execute using the default user's web-session authority. This contradicts the factory's stated isolation contract. It is not evidence of access beyond credentials already held by the server.

**Plan:** resolve named-profile credentials independently; fail clearly or use only that profile's explicit token route when its cookie is absent. Define and document environment-token precedence separately, and validate tenant identity when combining credentials.

**Acceptance:** real-factory tests cover missing, token-only, cookie-only, and hybrid named profiles with default credentials present. No named profile silently receives a default cookie. Existing default-profile behavior and session isolation remain covered.

### REV-02 · P1 · REST errors bypass secret redaction

**Reproduced.** [client.ts](../src/client.ts), lines 389–397, interpolates the entire non-success response body into `FusebaseApiError.message`; [helpers.ts](../src/tools/helpers.ts), `errorResult`, returns the message unchanged. Gate has a redactor and dedicated tests, but this REST path does not use it. A mocked HTTP 500 containing a synthetic Authorization value passed that value into tool output.

**Impact:** upstream errors that echo request configuration, credentials, or login links can disclose those values to clients and logs. This review did not observe a real secret disclosure.

**Plan:** centralize bounded public error formatting across REST, Gate, CLI, and tool boundaries. Preserve status, operation, and a safe correlation identifier; remove credentials and internal request configuration before any public rendering. Audit logging separately from the error object's internal fields.

**Acceptance:** synthetic nested headers, cookies, token fields, magic-link parameters, non-JSON bodies, and oversized errors are redacted and bounded through actual tool responses and captured logs. Useful non-sensitive diagnostics remain.

### REV-03 · P1 · npm distribution cannot run its install lifecycle

**Reproduced.** [package.json](../package.json), lines 23–27 and 58, packs only `dist`, README, and LICENSE but declares `node scripts/postinstall.mjs`. Running that lifecycle in the extracted tarball fails because the script is absent. [client.ts](../src/client.ts), lines 586–588 and 623–625, also dynamically imports auth helpers outside `dist`; they are neither compiled by the current `rootDir: src` build nor packed. The guide-fetch command depends on an omitted script and development tooling.

The local dry-run artifact additionally contains `dist/token-builder.js` and `dist/yjs-writer.js`, whose source files no longer exist. `build: tsc` does not remove stale outputs. A clean checkout may avoid those stale files, but a local release is not reproducible. Docker is intentionally token-oriented and should not claim browser refresh support merely by including the client class.

**Plan:** define the supported installed-package contract; compile/include required runtime helpers; make guide acquisition an explicit, production-usable command or ship a functional optional installer; build into a clean release directory. Declare directly imported dependencies such as `zod`, and set the MCP SDK minimum to the oldest version actually supported by the APIs used rather than `^1.0.0`.

**Acceptance:** create a tarball from a clean checkout, install it outside the repository with lifecycle scripts enabled and dev dependencies absent, start stdio and HTTP, list tools, and exercise the documented guide/auth paths. Compare packed JS modules with the intended output manifest. No stale modules, `.env`, credentials, scratch data, or unrelated product files are included.

### REV-04 · P1 · Sweep cleanup relies on names and can report success after deletion failures

**Code-confirmed.** [sweep-sandbox.ts](../tests/live/sweep-sandbox.ts), lines 18 and 128–150, treats broad words such as `Test`, `QA`, and `Validation` as ownership evidence. With `--clean`, it deletes both current leftovers and older “orphans,” including organization-wide databases, flows, and tokens. A legitimate resource named “Customer Validation” satisfies that predicate. Deletion failures are logged and swallowed, and the final leftover failure is disabled when `--clean` is set.

The sweep also reads bounded first pages (500 pages, 100 tokens, 200 tasks) and does not cover portal memberships, magic links, agents, or hosted products. Unknown creation timestamps do not qualify as current leftovers.

**Plan:** record exact IDs and ownership metadata in a durable per-run fixture journal. Only delete positively identified owned resources; report other candidates without deleting them. Exhaust pagination, verify absence after deletion, and fail when cleanup or enumeration cannot be proved. Recover interrupted runs from their journals.

**Acceptance:** fixtures resembling real customer resources are never selected by name alone; pagination and missing timestamps cannot produce false clean results; injected deletion failures fail the sweep; all owned resource kinds are accounted for. Use mocks first, then a dedicated sandbox run.

### REV-05 · P1 · Token-coverage mode can replay an ambiguous write

**Code-confirmed.** [harness.ts](../tests/live/lib/harness.ts), `callOnTwin` and `callTool` around lines 214–290, catches every token-twin failure and then performs the same call on the normal client. For a write that succeeds remotely but times out or returns malformed output, this can execute the write twice. This affects opt-in token coverage, not every normal live run. Production code already has more conservative fallback rules.

**Plan:** distinguish unsupported/auth-rejected operations from ambiguous completion. Never replay an uncertain mutation. Journal attempted writes before sending, preserve identifiers, and reconcile by fresh reads. Prefer separate fixtures for comparisons that intentionally exercise both modes.

**Acceptance:** a fake remote write that commits then times out results in exactly one mutation attempt, an explicit uncertain outcome, and recoverable cleanup information. Safe read fallback and clearly rejected operations retain useful coverage reporting.

### REV-06 · P1 · The repeatable portal email test leaves access behind

**Code-confirmed.** [data-validation.ts](../tests/live/data-validation.ts), lines 1290–1307, explicitly acknowledges that the opt-in email branch leaves a portal client behind. It invites the address and creates a magic link without a `finally` that revokes the link or restores membership/access. The general sweep does not inspect those resources.

**Impact:** enabling the test can create persistent access even when the overall suite reports success. The earlier manually supervised email validation did revoke its links and remove its disposable membership; that successful cleanup does not fix this repeatable branch.

**Plan:** move email validation into a disposable portal/workspace fixture; snapshot preexisting membership and never remove or downgrade an unrelated account. Journal and revoke issued links, restore access, and verify cleanup even after an assertion fails. Keep delivery and browser activation as separate evidence from API acceptance.

**Acceptance:** success, failed send, failed verification, and interrupted-run recovery all leave no new active link or unintended membership. Existing users and roles remain unchanged. Run the email stage only with explicit opt-ins and a designated test recipient.

### REV-07 · P1 · Deployment success does not prove the intended dashboard is live

**Code-confirmed.** [deploy-status-dashboard.ts](../scripts/deploy-status-dashboard.ts), lines 67–83, catches failed health checks, prints a warning, then prints the success banner and exits successfully. A 200 page with any `<title>` also passes, including an older deployment. The request has no explicit timeout. The target identity guard is useful but does not establish deployment completion.

The tracked [.githooks/pre-push](../.githooks/pre-push) also chains an optional, untracked local hook. In this checkout that hook deploys before the push completes; a later rejected push can leave the site ahead of the remote repository. Other clones do not receive that hook.

**Plan:** make verification fail closed with a bounded timeout and propagation polling. Publish a release manifest containing the full commit, build identity, and evidence identity; require the live site to match it. Keep deployment an explicit tracked command or a post-push workflow, and document rollback to a verified release.

**Acceptance:** HTTP errors, timeouts, stale 200 responses, and wrong commits produce nonzero exit status and no success banner. A fresh deployment is checked by manifest and browser smoke test. Failed pushes cannot silently publish an unpushed release. The previously deployed site was independently verified; this finding concerns the pipeline's future guarantees.

### REV-08 · P2 · Dashboard evidence can be stale, partial, or mixed across revisions

**Code-confirmed.** [test-all.ts](../scripts/test-all.ts), `recordResult` around lines 115–136, replaces one stage at a time while retaining all other stages. It records HEAD but not working-tree changes, so pre-commit results can be attributed to code different from the recorded commit. [generate-status-data.ts](../scripts/generate-status-data.ts), lines 98–123, aggregates every retained result without requiring a common revision or complete run.

Stage descriptions expose individual timestamps and commits, which helps inspection, but aggregate “Latest checks passed” and cleanup status can still mix old live results with new offline checks. The generator also hardcodes protocol `HEALTHY`, and [App.tsx](../apps/client-portal-dashboard/apps/status-dashboard/src/App.tsx), line 236, hardcodes cloud health. A historical token milestone says 14/129 while the later documented snapshot is 29/150.

**Plan:** record immutable run IDs, exact source identity including dirty state, stage selection, completion, runtime, structured counts, and cleanup outcomes. Publish current-revision evidence separately from historical evidence; mark missing/stale results explicitly. Derive service health from an actual dated probe or label it unknown. Keep historical milestones dated and distinct from current metrics.

**Acceptance:** dashboard fixtures for mixed commits, dirty trees, partial runs, failures, no results, and stale cleanup never show an unqualified current pass. An offline rerun cannot refresh the apparent age of live validation. Failure badges use failure styling.

### REV-09 · P2 · HTTP session capacity has no recovery policy for abandoned sessions

**Reproduced/code-confirmed.** [http-server.ts](../src/http-server.ts), line 89, accepts `NaN`, zero, negative, and partially numeric session limits. `NaN` disables the numeric cap; non-positive values reject all new sessions. Session entries are removed on transport closure, with no idle-expiry policy. A client that initializes and disappears without terminating the MCP session retains a slot. The local two-slot probe reached 503 after two abandoned initializations.

**Plan:** strictly validate finite positive integer limits; track session activity and expire idle sessions safely, closing associated server/transport resources. Account for in-progress initialization and failed connection setup when enforcing capacity. Bound graceful shutdown.

**Acceptance:** invalid settings fail startup; abandoned sessions expire and capacity recovers without restarting; active sessions are preserved; concurrent initialization cannot exceed the configured cap; shutdown completes with open or failed sessions. Existing authentication, Host, and Origin tests continue passing.

### REV-10 · P2 · Runtime data storage is inconsistent and unbounded

**Code-confirmed.** [crypto.ts](../src/crypto.ts), `getDataDir`, honors `FUSEBASE_DATA_DIR`, while [client.ts](../src/client.ts), lines 90–92 and 246, always creates the installation's `data/` directory for logs/cache. [helpers.ts](../src/tools/helpers.ts), `downloadRoot`, likewise defaults to installation-local downloads. Setting a separate writable data directory therefore does not make a read-only installation usable. Client construction can fail before an API call. Logs append indefinitely; the shared workspace cache merges entries without separating profile/tenant files.

**Plan:** centralize data-path resolution; put runtime writes under the configured data directory, with the explicit download override retained. Namespace caches appropriately, use atomic writes, and add bounded log retention and safe file permissions.

**Acceptance:** server startup, logging, cache updates, credential operations, and downloads work with a read-only install and writable external data directory. Profile/tenant cache contents stay separate; log size is bounded; filesystem failures have actionable, non-secret errors.

### REV-11 · P2 · Coverage bookkeeping can misclassify operations and restrictions

**Code-confirmed.** [harness.ts](../tests/live/lib/harness.ts), lines 366–421, maintains an independent `WRITE_TOOLS` allowlist and treats everything else as a read. `fusebase_direct_tool_call`, which can invoke arbitrary remote writes, is absent. Future tools can therefore escape write-proof accounting or be accepted as “reads” during verification. This is a structural gap, not evidence that every existing assertion is wrong.

[token-parity.ts](../tests/live/token-parity.ts), lines 54–65, counts any failure in a restricted-mode probe as `RESTRICTED`, including a timeout, network error, or malformed response. Its row checks can fail the suite, but they do not increment the harness assertion counters, hence a successful stage can report 0/0 assertions.

**Plan:** share explicit operation-effect metadata with the registry; classify dynamic calls by discovered operation or an explicit test declaration, defaulting unknown effects to unverified. Require a successful independent read for write proofs. Require an expected authentication/capability rejection for `RESTRICTED`, and report parity checks with structured counts.

**Acceptance:** every registered tool has a coverage classification; dynamic mutations cannot qualify as read-back; network/5xx/parse errors fail restriction checks; parity rows and assertion totals reconcile. Existing proven write checks retain their evidence.

### REV-12 · P2 · CI and the standard runner omit important release surfaces

Some behavior is covered through other paths, but focused results and manual hosted/email follow-ups do not enter the same evidence ledger. Calling the command “all live suites” overstates its scope.

Add selectable focused stages and structured recording for external/manual evidence. Keep email, account-wide changes, paid agent execution, and deployment opt-in; do not put production credentials in pull-request jobs.

**Acceptance:** breaking the dashboard or package lifecycle fails CI; a fresh clone can reproduce release checks; selected focused stages appear with explicit run identities; skipped/permission-blocked/manual checks remain visible. Node 22.19 unit coverage is now manually confirmed and should become continuous coverage.

### REV-14 · P3 · Shared transport and domain contracts remain difficult to maintain

**Code-confirmed maintainability issue.** `client.ts` and `extended-tools.ts` remain multi-thousand-line modules; root lint reports 394 nonblocking warnings, largely explicit `any`. Tool handlers repeat client acquisition and error rendering. Several adapters and tests depend on internal shapes, and effect/coverage classifications are duplicated.

**Plan:** after correctness fixes, extract domain adapters around a shared typed transport/error layer; introduce typed response boundaries and common tool registration metadata. Refactor in small behavior-preserving changes, prioritizing auth, portal, SQL, and agent contracts. Ratchet warnings down instead of suppressing them or requiring a large rewrite.

**Acceptance:** no new warnings; each extraction preserves existing contract tests, tool names/schemas, and relevant live behavior. Shared metadata drives annotations and coverage classification. Large unsupported architecture migrations are separate decisions.

## Upstream boundaries and investigations

These are not counted as newly confirmed local defects and should not be “fixed” by silently expanding permissions or replaying operations:

- **Token-only reach:** the prior measurement is 29/150 remote tools without cookies, not all 177 local tools. Inventory currently discoverable Gate/Dashboards operations, permissions, and supported schemas before selecting wrapper migrations. Prioritize high-use database/page operations; retain explicit unsupported behavior where no safe official route exists. Verify read/write/cleanup per migrated operation.
- **Paperclip permissions:** the tested token lacks the relevant Work-agent API access. Existing successful AI Assistant tests exercise a different API. Treat this as a permission boundary until an authorized credential with the required scope is available.
- **Agent stream reliability:** one prior response was rejected as malformed; its raw response was not captured. Root cause is unknown. Add bounded, redacted diagnostics and correlation IDs, then collect repeated-run evidence. Preserve strict completion checks and the warning to inspect an existing thread before retrying.
- **Cancellation and long calls:** agent execution can run for 240 seconds and CLI operations for several minutes; handlers do not consistently propagate MCP cancellation. Investigate cancellation before send, during execution, and after a possibly committed write. Return an uncertain-outcome identifier where cancellation cannot stop upstream work. Do not infer that a client timeout means nothing happened.
- **Hosted log delay:** prior runtime evidence arrived after roughly nine minutes. Poll for a correlated marker with a deadline and report pending/timeout honestly; an immediate empty log is not execution evidence.
- **Launcher distribution mismatch:** the previous production installer supplied a version different from the advertised launcher artifact, whose download returned 403. Recheck official distribution evidence before escalation; do not treat old observations as a fresh outage or install an unverified binary.
- **Container/browser and filesystem boundaries:** Docker packaging was inspected but not built in this review. Browser authentication on Alpine, symlink/junction containment, crash recovery, and resource exhaustion beyond the small HTTP probe require targeted validation. Static path checks and passing unit tests do not establish every adversarial case.
